我爱你

本博客是怎么诞生的

2026-05-12
技术共享
等闲识得东风面，万紫千红总是春。

简述我作为一个没有IT背景的人是怎么架设这个博客的。

这不是详细的教程，但你喂给AI（需要代劳架设网站的话，特指 OpenClaw 这样的 agent），它能看懂。

本博客的架设任务在我的 OpenClaw agent 里代号 T002。

一、最初的目标

我想要的是一个足够安静的地方放自己的私人记录，能按栏目分类，能保留 Markdown 的结构，能有一点自定义的审美，也能尽量低成本地维护。

更具体一点，它需要做到这些事：

  • 我在 Obsidian 里用最简单的 Markdown 语言写文章；
  • 文章可以同步到网站；
  • 网站要能显示中文、标签、前言和正文结构；
  • 网站要有搜索、RSS、私信入口和基础安全头；
  • 网站源码和部署过程要能回滚；
  • 网站最好还有一个大陆访问受阻时可用的静态镜像。

二、选择静态网站作为地基

这个博客没有一开始就做成数据库网站。我选择了静态网站。静态网站的意思是：文章先被生成成普通 HTML、CSS、JS 文件，再由服务器直接发给读者。

它的好处很直接：

  • 快；
  • 便宜；
  • 不容易坏；
  • 没有复杂后台；
  • 不需要每个读者访问时都查询数据库；
  • 更容易保护私密内容不被意外发布。

T002 使用 Hugo 生成静态网站。Hugo 读取 content/ 里的 Markdown，生成 public/ 里的网页文件。

Note
这里是Hugo 项目初始化、主题安装、目录结构设计、构建脚本编写，都可以由 AI 代理完成。人需要确认的是：栏目名称、公开内容边界、页面审美和隐私规则。

三、栏目结构

博客的公开栏目按内容性质分开。

当前主要结构是：

  • thoughts：蒹葭苍苍（世界）；
  • records：我行其野（我）；
  • fiction：灼灼其华（虚构）；
  • memo：薄言采之（随想）；
  • blog：木瓜琼琚（收录）；
  • love：我爱你。

这些栏目在网站上是左侧导航。Obsidian 里也有对应文件夹。同步时，脚本会把 Obsidian 顶层文件夹映射到 Hugo 的栏目目录。

Note
栏目映射表适合交给 AI 代理维护，但人必须检查一次。否则文章可能被同步到错误栏目，例如本该进“我爱你”的文章被放到普通 blog 里。

四、从 Obsidian 到 Hugo

我真正写作的地方是 Obsidian。网站不要求我每次都手动复制文章。T002 有一个同步脚本：

scripts/t002-sync-obsidian-blog.mjs

它做这些事：

  1. 读取 Obsidian 指定文件夹；
  2. 解析 Markdown 和 YAML front matter；
  3. 保留标题、标签、前言、描述和来源路径；
  4. 把 Obsidian 文件转换成 Hugo 文章；
  5. 按栏目映射放进 content/；
  6. 删除已经不存在的旧同步文章；
  7. 保持正文结构尽量接近 Obsidian。

这里最容易出错的是“看起来一样”。Markdown 的换行，在源文件里存在，不代表网页上会显示出来。浏览器默认会折叠普通段落中的单个换行。所以后来网站样式里加入了：

.article-body p { white-space: pre-line; }

这样，像诗歌里的短行换行，就能按 Obsidian 的视觉结构显示。

Note
同步脚本、front matter 解析、路径映射、构建检查，都可以由 AI 代理完成。人要重点审核文章显示是否符合原文气质，尤其是诗、段落、缩进和标题层级。

五、页面设计

这个博客没有走传统“卡片式博客”的方向。它更像一个 Obsidian 文档阅读界面。

设计原则是：

  • 少用装饰；
  • 用文字层级组织页面；
  • 用左侧栏做导航；
  • 用暗色主题作为默认阅读环境；
  • 不用很多彩色盒子；
  • 尽量让文章本身成为中心。

文章页支持标题折叠。脚本会把文章中的标题变成可展开、可折叠的层级结构。这样长文可以像笔记一样阅读。

Note
CSS、模板和折叠脚本可以由 AI 代理实现。人需要用截图验收，因为“好不好看”不能只靠代码检查。

六、部署到 Cloudflare Worker

本博客主站部署在 Cloudflare Worker 上。Hugo 生成 public/ 后，Wrangler 把静态资源上传到 Worker。

当前主站地址是：

https://heptapodb-blog.wengerfan-asabridge.workers.dev/

Worker 的作用不只是托管文件。它还加了一层安全外壳。

例如：

  • 内容安全策略；
  • 防止页面被嵌入；
  • 限制浏览器权限；
  • 控制缓存；
  • 保护静态资源的响应头。
Note
构建、部署、检查 HTTP 状态码、检查安全响应头，都适合由 AI 代理自动做。Cloudflare token、账号权限、DNS 和域名绑定则必须由人明确授权。

七、GitHub 源码备份

T002 源码保存在 GitHub 仓库中。每次重要修改后，会提交 commit，再 push 到远端。

这带来三个好处：

  • 出错可以回滚；
  • 改动有历史记录；
  • 以后换设备或重建环境更容易。

但不是所有文件都应该进 GitHub。例如：

  • token；
  • 私密 notes；
  • 本地管理器数据；
  • 临时构建输出；
  • 用户私信原文。

这些都应该留在本地或被 .gitignore 排除。

Note
AI 代理可以写 .gitignore、检查 diff、提交代码。人要确认没有秘密、客户资料或私人内容被提交。

八、大陆备用镜像

后来发现，workers.dev 在中国大陆可能访问不稳定。于是做了 GitHub Pages 静态镜像。

镜像地址是：

https://wengermyy.github.io/heptapodb-blog-mirror/

这个镜像只放生成后的静态网页。它不公开完整源码。它也不能使用私信和订阅功能。页面顶部会说明：这是大陆访问受阻时可用的备用静态镜像。

Note
创建公开 mirror repo、生成静态文件、推送镜像、检查资源路径、用截图做视觉验收，都可以由 AI 代理完成。是否公开仓库、是否创建新 repo，必须由人批准。

九、私信和订阅

博客有私信和订阅入口。但这部分最敏感。

因为一旦接受读者输入，就涉及：

  • 隐私；
  • 垃圾信息；
  • 邮件发送；
  • 存储位置；
  • 删除和保留期限；
  • 是否可能泄露 IP 或用户代理信息。

所以 T002 的做法是：功能可以有，但每一步都要有边界。能静态完成的部分先静态完成。需要后端、邮件、数据库或长期保存的部分，必须单独设计和批准。

Note
AI 代理可以写表单、后端、邮件测试和安全检查。人必须决定数据如何保存、保存多久、谁能看、是否真的需要收集。

十、自动化同步

T002 后来有了定时同步。定时任务会在固定时间检查 Obsidian 文件夹。

如果文章有变化，就可以：

  1. 同步到 Hugo；
  2. 构建网站；
  3. 运行检查；
  4. 部署主站；
  5. 推送 GitHub；
  6. 更新镜像。

这让博客接近“写完就能上线”。

Note
关键内容、公开发布、隐私边界和外部账号动作，都需要明确规则。

十一、这个博客真正的架构

如果把整个系统压缩成一句话，它是这样：

Obsidian 负责写作，Hugo 负责生成网页，Cloudflare Worker 负责主站发布，GitHub 负责版本记录，GitHub Pages 负责备用静态镜像，AI 代理负责把重复、易错、可验证的步骤自动化。
